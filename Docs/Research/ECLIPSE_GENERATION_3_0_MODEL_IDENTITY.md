# ECLIPSE 3.0 · 新模型身份与生产门禁

**Gomoku 应用版本：V2.0.0（Build 200）**  
**新上传模型代际：ECLIPSE 3.0（R07 34D 研究候选）**

这是两条独立的版本线：App V2 不代表模型 V2；R07 的研究修订号也不应直接充当产品版本号。正式 3.0 检查点必须通过 SHA-256、特征向量 ABI、一致性与独立比赛验证。

## 已实现
- 五份独立 R07 模型确认为同一个 ECLIPSE 3.0 **研究系列**（244/249/259/274/289 棵树），原始权重文件字节与 SHA-256 不变；R04 239-tree 只作为历史基线保留。
- iOS 资源 `ECLIPSE_3_0_RESEARCH_MODELS.json` 描述新模型代际、34D 输入维度、五份确切 SHA、研究状态和升级要求。
- Swift `EclipseGeneration3ResearchCatalog` 在读取配置时严格校验新代身份、树数、源文件名、哈希格式、未晋级状态和 8/9 失败门禁。没有通过时不显示为有效模型。
- 开发者 HUD 将 ECLIPSE 3.0 的*研究状态*与真正执行的已加载 V9 Astra/Sol 2.0 SHA 分开展示，不修改正式对局/训练归属。
- Python 测试逐字节哈希 R07 五份权重，关联原研究 `MODEL_MANIFEST.json`；iOS XCTest 防止通过伪造 JSON 的 `production_enabled` / `ios_runtime_loaded` 将权重“升级”。

## 严禁混淆的边界
- 本仓库目前缺少原 R04 26D `data_pipeline.features` 的完整可独立执行实现。现有 34D 适配层需要先调用该函数再补 8D；因此**不能在不复原 26D 输入与全量树的情况下宣称 3.0 模型已经在 iOS 真实推理**。
- 3.0 R07-249 在当前研究测试仅通过 8/9 门禁，真人历史落点 Top-1 有 1/40 回归。1,024 局是深度 0 的研究排序器对弈，不是现役 V9 原生 C++ 搜索；未获得生产晋级资格。
- 暂无可信的 3.0 Sol 蒸馏权重；不得复制 2.0 Sol SHA 或把 2.0 计算策略改名成 3.0。
- 保持 `EclipseModelID` 正式模型选择器的已验证身份原则，未满足原生加载校验的 3.0 不出现在正式可选/可计分列表中。
- 原始 `.vltrain`、用户和朋友棋谱、个人 SQLite、未脱敏的真实局面测试集依旧不进入公开 App/IPA。

## 后续真实晋级步骤
1. 引入并审计原 26D 基础特征实现，重建严格一致的 34D 特征 ABI（含对比 LightGBM 官方推理的数值测试）。
2. 编译并在 iOS 真正加载 R07 3.0 原始权重，验证逐树阈值/叶值、SHA、线程安全和棋盘合法落子。
3. 补齐 9/9 强制战术门禁以及独立盲测，不以已多次复用的数据集证明模型棋力提升。
4. 在相同硬件、预算、交换先后手的受控比赛中比较 ECLIPSE 3.0 与 2.0 的 Elo 区间、漏防、P50/P95、功耗，另评估 Sol 3.0 是否存在蒸馏模型。
5. 检查 iOS XCTest、私有数据扫描和真实 Release IPA 后才允许晋级生产。

**当前状态：3.0 身份与完整研究权重来源可验证；3.0 原生生产推理/晋级尚未完成。**
