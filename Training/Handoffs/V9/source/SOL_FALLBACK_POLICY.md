# Sol 降级替补策略（迭代 Agent 接线前必须审查）

## 产品定位

- 同代 V9 Sol 160 树由 Astra 314 树的学习监督蒸馏，是**独立拟合权重**，不是单纯把 Astra 120ms 改成 Sol 60ms。
- Sol 的定位是节省模型权重磁盘大小、模型推理时间和搜索资源，并且在 Astra 因设备资源/运行约束无法安全运行时提供可用候选。
- **不保证 Sol 能解决 Astra 无法获胜的局面。** 如果 Astra 对局不利，可以让用户选择 Sol 或研究不同策略，但不能把“轻量化”误写为“自动棋力反超”。

## 状态迁移（须真实测量并获 R15 架构批准）

1. 正常：Astra 请求下棋；若当前设备无法满足实测的内存/热状态/延迟要求，建议在**新对局开始前**选择 Sol（或提示用户选择经济模式）。
2. 若 Astra 中途搜索超时，**优先返回 Astra 已完成深度的安全合法着法**。不能仅因为超时就用 Sol 结果覆盖、掩盖 Astra 的身份和统计。
3. 若 Astra 初始化失败、加载错误或设备已不适合继续，取消异步搜索、失效 generation token；当前 R15 切换产品模型会重置对局。**在未获授权扩展逐手模型归属/签名的 archive schema 前，不允许偷偷在同一对局换成 Sol**。
4. 若以后授权实现逐手降级：每一步记录 requested_model / executed_model / checkpoint_sha256 / fallback_reason / elapsed_ms / completed_depth / stop_reason；对局签名、学习归属与恢复策略均须保持可审计并由用户理解。
5. 资源等级上限是安全界限，不是耗尽目标。必胜必防安全门永不被轻量化跳过；训练报告分别统计提前收敛和硬超时。

## 参考观测与缺口

- V9 Astra：314 树、691578 字节；V9 Sol：160 树、261150 字节；磁盘节省 **62.24%**，不是内存节省比例。
- 8 局相同 120ms 上限内部研究对局：Astra 对 Sol 4:4，Astra 搜索硬中断 26 次、Sol 0 次。样本小且是非 R15 搜索器，不能外推真机。
- **iOS/Swift-C++ 实际部署性能、真机内存、温度、总延迟、费率尚未测量，阈值不得拍脑袋写成已批准数值。**

## 推荐保留的回滚顺序

- 首选研究候选 Astra V9 / Sol V9：仅在独立实验环境。
- 遇到必防排序反例或资格门失败时，回退到 Astra V8 254 树进行旧基线对照；Sol V8 120 树保留为历史对照。不能将旧“安全排序基线”冒充已通过 Swift 天元 6× 的生产模型。
